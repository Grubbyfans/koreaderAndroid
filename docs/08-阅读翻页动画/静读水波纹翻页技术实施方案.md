# 静读水波纹翻页技术实施方案

日期：2026-11-27。状态：阶段一源码调研完成，待评审；尚未开发、构建或执行测试。

## 1. 结论与范围

推荐在现有原生渐变翻页链路中增加 `ripple` 动画策略，复用预览页面、快照池、手势、帧时钟及提交事务。新增小型 Canvas 渲染器，采用目标页 BitmapShader 与柔性渐变遮罩的 ComposeShader 混合，实现 Directional Soft Wipe。不增加依赖，不提高 minSdk 26，不改 EPUB 引擎、分页系统或同步协议。

两页始终保持原位，翻下一页暂定从右向左刷新，上一页镜像，符合当前左滑下一页／右滑上一页的方向。默认实验参数建议先用 Kindle 风格 160ms／48%，内部保留掌阅风格 320ms／25%；最终方向观感及默认参数由用户在三星 S25+ 上确认。

按用户追加要求，全局设置和阅读页排版面板均展示完整五项：**无动画、滑动、渐变、iOS 仿真、水波纹**。共用现有 `page_animation` 配置，不新增配置页面或面向用户的预设切换。

本阶段仅新增本方案并更新文档索引；不修改业务代码、版本号或构建配置，不操作设备，不打包。

## 4. 渲染方案

### 4.1 技术选择

优先复用渐变动画已有的两页快照、覆盖层及原位绘制机制。现有 fade 只有全局 alpha，无法直接表达局部混合；因此仅补充 Canvas 遮罩渲染能力：

1. 按现有 bounds 原位完整绘制旧页。
2. 用目标 Bitmap 创建 `BitmapShader(CLAMP, CLAMP)`。
3. 用 `LinearGradient` 表达从不透明到透明的柔性权重，使用 CLAMP 保持两端稳定。
4. 用 `ComposeShader(目标页Shader, 遮罩Shader, PorterDuff.Mode.DST_IN)` 得到带局部 alpha 的目标页。
5. 使用正常 SRC_OVER 将结果绘制到旧页上，得到 `Old × (1-mask) + New × mask`。

ComposeShader 在 shader 内混合，不在画布上对已经绘制的旧页执行 DST_IN。该方案不需要额外全页 Bitmap 或 saveLayer 离屏层，也不进入现有 iOS Mesh/GLES 路径。Canvas 实际执行及纹理驻留由系统管理，只承诺代码不逐帧重建 BitmapShader、复制页面或显式重复上传纹理，不能保证驱动绝无重传。

默认沿用现有不透明页面快照语义；若测试书样发现透明底，准备阶段使用当前实际阅读背景完成合成，不用固定白色填充。遮罩 RGB 不参与正文配色，不做整页灰度化、亮度变化或颜色滤镜。彩色插图、dark、sepia 及当前管线支持的字体／背景照原样混合，不扩展主题系统。

### 4.2 遮罩算法与方向

以从左向右刷新为标准坐标，页面宽度 W，柔性带宽 B = W × transitionWidthRatio：

```text
p = clamp(progress, 0, 1)
s = p × (W + B) - B
u = clamp((s + B - x) / B, 0, 1)
mask = u × u × (3 - 2 × u)
```

下一页从右向左时令 `x = W - screenX`；上一页从左向右时令 `x = screenX`。正反向仅改变遮罩坐标，不移动页面纹理。

普通两色 LinearGradient 只有线性 alpha，不能直接称为 Smoothstep。拟在准备阶段生成固定 33 个等距色标，alpha 取 `1 - smoothstep(t)`，通过多色标 LinearGradient 对三次曲线作分段线性近似。色标和位置数组集中缓存，不在绘制帧内生成；这是非逐像素的小型初始化计算。若后续实测发现色阶可见，先调整固定色标数量，再评估其他实现，不默认改用 RuntimeShader。

Gradient 定义在局部 0～B；准备阶段按尺寸建立目标 Bitmap 到视口的矩阵，按方向配置渐变镜像；每帧仅平移渐变到 s、更新进度并 invalidate。Matrix、Paint、Shader 均复用，不重建两页纹理、不创建每帧对象集合。

端点显式处理：p≤0 只绘制旧页；p≥1 只绘制目标页。中间使用上述遮罩，带外自然为 0 或 1；不依赖最后一个采样像素碰巧达到端点。结束后仍用 `showPage(commit)` 保留清晰末帧，等主页面视觉就绪才撤除覆盖层。取消则恢复旧页，不提交目标位置。

### 4.3 资源与生命周期

新增渲染器借用当前／目标 Bitmap，不拥有或 recycle 快照。`prepare()` 重置模式、方向、进度及 shader 资源；`showPage()` 明确显示目标或旧页；`clear()` 释放 shader 对 Bitmap 的引用并清理模式。尺寸、主题变化先取消旧事务，再失效旧布局和准备资源。

水波纹绘制失败必须纳入 Overlay 现有的 generation 校验及异步 `onRenderFailure` 通知范围。当前异常捕获主要围绕 iOS 分支，不能把新分支放在捕获范围外。失败后先撤除覆盖层、释放资源，再根据事务状态决定是否无动画完成一次导航，不在 onDraw 中导航或拆 View。

## 5. 动画参数及手势接入

新增一个轻量 `RippleTurnSpec.kt`，集中存放以下两组内部常量与共享曲线；不增加设置存储键。

| 参数 | Kindle 实验预设（建议首版默认） | 掌阅实验预设 |
| --- | --- | --- |
| durationMs | 160 | 320 |
| transitionWidthRatio | 0.48 | 0.25 |
| movementInterpolator | Linear | Linear |
| opacityInterpolator | Smoothstep 色标近似 | 同左 |
| 位移／扭曲／阴影 | 均为 0，不提供多余可调项 | 同左 |

预设仅影响 ripple，fade 的 360ms／FastOutSlowIn 与 iOS 参数保持原样。沿用 `MonotonicFrameClock` 和 `PageTurnFrameTime` 驱动 Animatable，边界随逻辑进度线性移动。

160ms／320ms 指普通点击的基础时长。沿用现有连续点击 2 倍及催促完成 3 倍规则时，实际剩余时间会缩短；这也影响真机观感，应单独验收，不能将任何场景都宣称为固定 160ms。

复用 fade 已有的拖动进度 `clamp(dx × -direction / width, 0, 1)`，以及原有 0.1 提交阈值；ACTION_CANCEL 回退。不重新设计手势识别、速度判定或阈值。手动松手后按剩余进度比例折算 ripple 的收尾时间，避免短距离收尾仍播放完整基准时长；该计算只作用于新模式。

设置使用字符串 `ripple` 贯穿 DataStore、Activity、控制器与 bridge。全局设置改为可横向滚动的完整选项行，防止五项挤出窄屏；沿用原有选中、保存和点击方式。阅读页面板复用现有横向滚动行并统一上述五个名称，不另加预设选择 UI。

当前确定的动画入口为点击和拖动；外部目录、CFI 跳转等现有导航继续取消覆盖层并直接执行。若存在其他共用 `tap(direction)` 的翻页入口自然获得新效果，不为扩大动画覆盖范围改造外部导航规则。

## 6. 连续翻页、提交与异常处理

### 6.1 保留现有连续翻页策略

- `pendingTurn` 只存最新方向，最多一个正在执行事务和一个待处理方向，不累积无限动画队列。
- 动画期间新输入触发 finishVisual，加速剩余动画；不直接跳掉事务或提前重复提交。
- 反向输入覆盖 pending 方向：先完成已进入收尾的当前翻页，再处理最新反向请求。不把“反向点击”改成当前事务回滚。
- 停止输入后最多处理已有活动页和最后一个 pending 请求；不会继续回放所有历史点击，也不承诺每一次快速点击都逐一翻页。
- 仍由 `transaction.commit(token)` 允许一次主导航；末帧保持到提交的 Promise、CFI 变化及视觉回调完成。已有提交等待上限 5 秒。

这些机制已有源码及事务／帧时钟单测支撑，但新增模式的端到端表现尚未验证。预览未就绪时会等待，最坏可受到预览准备超时影响；水波纹不承诺消除既有冷启动／跨章等待，也不全局重构队列。

### 6.2 仅针对 ripple 补齐准备失败降级

控制器包装 PreviewPageProvider 的 onFailure 回调，保留原来的错误上报；仅在 ripple 下记录本轮预览失败标记。通过既有 onPrepared／drain 回调，准备结束后检查：

1. 目标快照仍有效：按原流程动画。
2. 无目标且有明确准备失败：只消费最新一个 pending 方向，走现有无动画 nextPage/prevPage；外部导航取消旧事务并清理覆盖层。
3. 无目标且准备正常结束：按书籍边界处理，不循环重试、不伪造目标页。

失败标记随 open、布局失效、重新准备和 cancel 重置，避免旧错误影响新页面。发生错误后可用保守方式禁用本轮 ripple 预览，后续翻页暂走无动画，换书／重新打开后恢复；需覆盖等待中的拖动释放。优先在控制器局部实现，不改变 provider 公共职责，也不顺带改变 fade／ios_curl 的既有失败行为。

如实施时发现 provider 现有回调不能可靠关联准备代次，才补充最小失败状态／代次信息；不依赖错误文本猜测边界，不新增第二套导航队列。该点属于需重点验证的局部改动。

### 6.3 场景处理及限制

| 场景 | 处理方式 |
| --- | --- |
| 点击／双向拖动完成 | 复用事务与唯一提交；ripple 只替换画面计算。 |
| 短拖、ACTION_CANCEL、多指介入 | 沿用取消路径；不新增目标页提交，清掉遮罩及待处理手势。 |
| 章节首尾／跨章 | 使用预览的 adjacent 和现有 paginator；书籍边界不启动动画；跨章资源尚未齐备时等待准备或明确失败后降级。 |
| 快照／渲染失败、OOM | 先释放视觉状态；未提交的点击或确认手势最多无动画完成一次，取消手势不导航；日志保留异常。 |
| 后台／返回前台 | 已有 ON_STOP 调 suspendPreview，取消并关闭预览；ON_START 重开并准备。保留现有 ON_PAUSE 进度保存时机。 |
| 退出／换书／外部导航 | close/cancel/open 使 generation 失效并释放引用；不允许旧回调恢复遮罩。 |
| 主题、字体、尺寸或横竖模式变化 | 先取消动画，再重建布局版本和快照；不跨配置复用旧纹理。 |
| 提交超时或提交期间中断 | 沿用 finishAnimatedCommit 发布已收到的位置事件并清理门闩；不得再次盲目调用 nextPage 重试。 |

取消协程不等于撤销已经发给 WebView 的 JS 导航。COMMITTING 期间的后台／主题变化等必须核对最终主页面 CFI 与已发布事件，不能承诺强行回到旧页；恢复后以主 WebView 实际位置重新准备。此次不新增云端写入或改变覆盖同步规则。

## 8. 阶段二验证与交付计划

本需求明确要求阶段二使用模拟器定向验证，且默认不操作用户真机；按本任务要求执行，覆盖项目一般“连接手机即安装”的默认规则。本阶段没有执行下列命令，也没有探测或启动模拟器。

### 必要验证

1. 定向 JVM：遮罩 p=0/1、带外稳定、正反镜像与随进度单调替换；ripple 设置差量保存；原事务及加速时钟用例继续验证唯一提交、过期 Token 和取消行为。
2. 定向 Node：bridge 的 ripple 原生接管、切换其他模式清理属性，运行现有 native-page-turn 用例确认普通分页延迟和原生提交锁定行为未变。
3. 固定模拟器＋独立测试包：全局／阅读页五项展示、保存恢复、点击前后翻、长拖完成及短拖取消、跨章／书籍边界、快速同向及交替点击、模式切换、退出重进、后台返回、配置／尺寸变化。记录 CFI、提交次数和事务完成，不用只检查“页面有变化”作为通过依据。
4. 针对异常路径模拟一次准备失败及提交超时，确认失败请求有界、旧遮罩撤除、后续可翻页且无重复提交。所有注入仅限隔离测试会话，验收后撤除，不新增导出调试入口。
5. 视觉定向：light／dark／sepia、不同字体、彩色图片；只在判断遮罩边界和结束闪烁确有必要时查看少量画面，不生成证据包。自定义背景仅验收项目当前实际支持的内容，不为此新增设置。
6. 相关回归仅覆盖 fade、ios_curl、none 及切换／位置事件，保留 slide 行为；不执行全项目测试或云端覆盖同步。通过主页面事件与代码检查确认预览无持久化副作用，真实云同步未测需注明。

可复用 `tests/fixtures/page-preview/` 的合成多章 EPUB（含 SVG）；复用 PageTurnTiming 和现有 `tests/adb-page-turn-timing.py` 的定向思路。该脚本要求打开阅读器、硬编码 1080×2340 坐标并会改变阅读位置，且缺少取消／跨章／位置正确性断言；不能原样当作完整自动验收，必须指定模拟器并核对尺寸，必要时做最小适配。

测试任务以新增用例实际归属为准，计划范围为 app 的 RippleTurnSpecTest／ReaderSettingsTest、reader 的 PageTurnTransactionTest／PageTurnVisualTest，以及 `node --test tests/native-page-turn.test.mjs`。不执行 `tests/*.test.mjs` 或所有模块测试。Canvas 真正混合结果不能仅靠纯 JVM 数学测试证明，需模拟器实际绘制核对。

### 性能判断

比较相同模拟器、书样、缓存条件下的首动时延和完成时延，利用现有 ReaderTurnTiming／gfxinfo 看短时卡顿与内存趋势；不把有限采样等同长期无泄漏或真机 120 FPS 保证。

重点核对新增绘制循环无 Bitmap 分配、截图、排版及 Shader 重建。现有 prepareAhead 若在 160ms 窗口引发主线程卡顿，只在 ripple 模式下将新邻页捕获延后到视觉结束，复用同一 provider；同时比较连续翻页准备时间，避免为了减少单帧卡顿增加明显的下一次等待。是否需要此调整由定向测量决定，不先改全局预加载策略。

### 打包交付

相关检查完成后递增届时版本，构建 `./gradlew :app:assembleTtsTestDebug`。独立包名 `com.yuezhou.reader.tts.test`、应用名“静读测试版”，不覆盖正式版或删除用户数据。模拟器验证仅使用合成书样与隔离数据，真机不自动安装或操作。

预期产物：`app/build/outputs/apk/ttsTest/debug/app-ttsTest-debug.apk`。最终交付提供实际 APK 绝对路径、版本／安装状态、采用预设、简洁总结及真实验证结果。S25+ 的流畅度、刷新方向观感、文字重叠柔和度、默认参数和长期稳定性保留用户验收；构建成功不等于验收通过。

## 9. 风险及评审事项

| 风险 | 应对与边界 |
| --- | --- |
| 名为水波纹却呈现波浪／折射 | 使用原位方向性柔性擦除，不引入变形、缩放、阴影。 |
| 渐变硬边或可见色阶 | 固定多色标近似 Smoothstep；端点显式全旧／全新；在设备上核对，必要时仅调色标密度与带宽。 |
| 深色／图片背景出现亮度跳变 | 同坐标原色 alpha 混合，不套灰度滤镜；确保不透明快照，禁止硬编码白底。 |
| 额外离屏层和纹理成本 | BitmapShader＋ComposeShader 直接绘制，沿用三页快照池，clear 释放引用；实际 GPU 行为仍待运行验证。 |
| 新模式冷缓存吞输入 | 对明确准备失败局部无动画降级；正常准备等待沿用现有策略，边界不反复重试。 |
| 高频反向、取消或提交期间变化 | 复用单 pending、事务代次和末帧保护；已发出的 JS 导航不重试、不伪装已回滚。 |
| 预加载抢占主线程 | 先复用并测量，必要时只调整 ripple 的捕获时机；不承诺零冷缓存等待。 |
| 厂商视觉差异 | 视频拼图仅做定性参考；两组初值共用算法，用户体验后调整默认值。 |

评审建议批准：现有渐变链路＋Canvas 组合 Shader、暂定 Kindle 160ms／48%、前进右向左／后退镜像、全局与阅读页完整五项、明确失败的局部降级，以及仅隔离模拟器的定向验证。评审通过后一次完成阶段二功能、必要回归及测试 APK；当前等待确认，不提前实施。
